Orientation

Twelve layers, twelve questions

The ecosystem looks like chaos because it is drawn as a logo cloud. It is not chaos — it is a dozen layers, and each one answers exactly one question about your system. If you can name the question, you can place any tool anyone throws at you, including ones that did not exist last week.

🗺️ The ecosystem, by layer

interactive

Click a layer. It cycles on its own until you touch it.

💡
The thing that actually gets tested. Nobody senior is checking whether you memorised logos. They are checking whether you can hear a problem and name the layer it belongs to — and then say honestly which tool you would reach for and what it would cost you. Tools change every quarter. The twelve questions do not.

❓ One question per layer

  • What produces the words? → the LLM layer
  • Who decides what happens next? → agentic orchestration
  • Where do the facts come from? → RAG
  • How does text become a number? → embeddings
  • How does the model reach my systems? → MCP and tools
  • What stops it doing something stupid? → AI security and guardrails
  • How do I know what it did? → observability and evals
  • What does it remember next time? → memory
  • What runs the loop in production? → agent SDKs and runtimes
  • What triggers it, and what happens after? → automation and workflow
  • Where do the vectors live? → vector databases
  • How does a human actually reach it? → the app and serving layer
⭐

Key point

Name the layer before the tool. Layers outlive logos. A tool that did not exist last quarter still belongs to one of these twelve questions, and placing it correctly is the skill being tested — not recalling a name.

Judgement

Add one rung at a time

The strongest thing you can demonstrate in a system-design round is restraint. Every tool on the map is also a thing to operate, secure, upgrade and pay for. This is the order to add them in, and the trigger that justifies each one.

🪜 The ladder

Stop at the rung that solves the problem you actually measured.

✅ Reasons that justify a new tool

  • A measured failure the current stack cannot fix.
  • A compliance or residency requirement with a name attached.
  • A cost curve you have actually plotted and crossed.
  • A latency SLO the current design misses.
  • An operational burden that is now bigger than the vendor bill.

🚩 Reasons that do not

  • It was on a diagram someone shared.
  • Everyone in the meeting had heard of it.
  • It might be needed later, at a scale nobody has forecast.
  • The current thing is boring.
  • The demo was very good.

📌 If you remember five things

  • Name the layer before the tool. Layers outlive logos.
  • Retrieval quality beats model quality, and reranking is the cheapest fix.
  • Irreversible actions are gated in code, never in a prompt.
  • Instrument before you optimise, or you will tune the wrong stage for a month.
  • Every tool you add is a system to operate. The best architecture is the smallest one that meets the requirement.
