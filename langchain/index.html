Chapter 1 · Foundations

A framework is a trade, not a gift

LangChain gives you one interface over every model provider, plus the plumbing for retrieval, tools, streaming and tracing. In return you take on an abstraction layer to learn and to upgrade. Whether that is a good trade depends entirely on what you are building — so let's compute it rather than argue about it.

⚖️ What do you actually need?

interactive

Tick what your project requires. The line counts are rough but the ratios are honest — they reflect the plumbing you would otherwise write and maintain yourself.

🧩 The one idea: Runnable

Every LangChain component — prompts, models, parsers, retrievers, tools, whole chains, entire graphs — implements the same interface:

runnable.invoke(input)      # one in, one out
runnable.stream(input)      # yields chunks
runnable.batch([a, b, c])   # concurrent
await runnable.ainvoke(x)   # async

runnable.with_retry()
runnable.with_fallbacks([other])
runnable.with_config(run_name="grade")

That uniformity is the whole design. It is why | works, why streaming reaches every step, and why a chain of chains is just another chain. Learn this one interface and most of the library stops needing to be memorised.

📦 What's in the box

  • Model interface — chat models, embeddings, one API across providers.
  • Prompts — declared templates with named, validated variables.
  • Output parsers — string, JSON, or schema-validated objects.
  • Retrieval — loaders, splitters, embeddings, 40+ vector stores.
  • Tools & agents — a tested tool-calling loop instead of your own.
  • LangGraph — stateful graphs with cycles, checkpoints and interrupts.
  • LangSmith — tracing and evaluation, usable on its own.
🎯
Install per-provider packages, not one giant one. langchain-core plus langchain-anthropic is a much smaller surface than langchain[all] — and it upgrades far more calmly.
Chapter 2 · Foundations

Everything is a list of messages

A chat model takes a list of messages and returns one message. That is the entire contract, and it is identical across every provider LangChain supports — which is exactly what makes swapping them a one-line change.

🔀 Swapping providers

from langchain_anthropic import ChatAnthropic
model = ChatAnthropic(model="claude-opus-5", temperature=0)

# same interface, different package:
# from langchain_openai import ChatOpenAI

    SystemMessage("You are a terse SRE assistant."),

# -> AIMessage(content="...", usage_metadata={...})

The chain built on top of model does not change at all. That portability is one of the strongest arguments for the framework — and it is the one people most often discover they needed after hard-coding a provider.

A prompt with a contract

An f-string is a string. A template is an object that declares its inputs, validates that you supplied them, composes with the rest of the chain, and shows up in your traces as a step you can inspect. The difference matters most at 2am.

💬 The message form

Most real prompts are built from messages rather than one string, so roles and history stay intact:

from langchain_core.prompts import (
    ChatPromptTemplate, MessagesPlaceholder)

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a support engineer at {company}."),
    MessagesPlaceholder("history"),
    ("human", "{question}"),
])

prompt.invoke({
    "company": "Northwind",
    "history": [HumanMessage("hi"), AIMessage("hello")],
    "question": "SSO keeps bouncing me",
})

Note MessagesPlaceholder takes a real list of messages. Flattening a transcript into one string throws away the role structure the model relies on.

Chapter 4 · Composing

What the pipe actually does

prompt | model | parser builds a RunnableSequence: each step's output is the next step's input. Because the result is itself a Runnable, you get streaming, batching, async, retries and fallbacks across the whole chain for free — and you can drop it inside a bigger chain without ceremony.

⚠️
The honest downside. LCEL is dynamically typed glue. A mismatch between two steps surfaces at invoke time, often as a confusing error deep inside a lambda. Keep chains short, name every step with .with_config(run_name=...), and test steps in isolation — prompt.invoke(x) works on its own, and bisecting a chain is much faster than staring at it.
Chapter 5 · Composing

Stop parsing prose. Constrain generation.

A parser cleans up after the model. Structured output changes what the model is allowed to produce in the first place — the schema goes over as a tool definition, and you get back a validated object instead of a dict you hope has the right keys. Once you have seen both fail, you stop reaching for the parser.

🧾 Four ways to get data out

interactive

Same task — pull a lead's details out of a message. Step through the options, including the one that blows up on a Tuesday.

✅ How to actually do it

from pydantic import BaseModel, Field
from typing import Literal

class Lead(BaseModel):
    """A sales lead extracted from a message."""
    name: str = Field(description="person's first name")
    company: str
    intent: Literal["pricing", "support", "other"]
    urgency: int = Field(ge=1, le=5)

chain = prompt | model.with_structured_output(Lead)

lead = chain.invoke({"text": "..."})
lead.urgency   # an int, validated, typed

The field descriptions and the class docstring are sent to the model. They are prompt engineering — a vague urgency: int gets you a vague number.

📋 Rules of thumb

  • Prefer with_structured_output whenever the model supports tool calling. That is nearly always.
  • Describe every field. The description is the only hint the model gets about what you meant.
  • Use enums and ranges. Literal[...] and ge/le turn a free-text guess into a constrained choice.
  • Keep schemas flat and small. Deeply nested models measurably lower extraction accuracy — split into two calls instead.
  • Temperature 0 for anything whose output feeds code.
  • Validation failing often is data, not noise. It usually means the schema does not match reality — add an "other" case rather than retrying harder.
Chapter 6 · Retrieval

Where RAG quality is actually decided

Everyone tunes the prompt. Almost nobody tunes the splitter — and chunking decides what can be retrieved at all. A fact cut in half across two chunks is a fact your system cannot answer about, no matter how good the model is.

Chapter 7 · Retrieval

Search by meaning, not by keyword

An embedding model turns text into a vector; similar meanings land near each other. A vector store indexes those vectors and answers "what are the k nearest to this one?" — which is how a question about "undoing a release" finds a document that says "rollback".

🔍 Similarity search, live

interactive

Eight documents from a fictional engineering handbook. Type a question — or ask something the handbook says nothing about, and watch what still comes back.

🗄️ Store and retrieve

from langchain_chroma import Chroma

store = Chroma.from_documents(chunks, embeddings)

retriever = store.as_retriever(
    search_type="mmr",              # diversify results
    search_kwargs={"k": 4, "fetch_k": 20},
)

retriever.invoke("Can I deploy on a Friday?")
# -> [Document(...), Document(...), ...]

A retriever is just a Runnable that takes a string and returns Documents — which is why it drops straight into a chain with |.

📈 Making retrieval better

  • Hybrid search. Vector similarity plus keyword (BM25) beats either alone, especially for names, error codes and IDs — which embeddings are genuinely bad at.
  • MMR (maximal marginal relevance) stops all k results being near-copies of the same paragraph.
  • Metadata filters. {"team": "infra", "year": 2026} narrows before you search. Cheap and effective.
  • Reranking. Fetch 20, rerank with a cross-encoder, keep 4. The single biggest quality win in most RAG systems.
  • Tune k. More chunks is not more knowledge — it dilutes the prompt and raises cost. 3–5 usually beats 10.
⚠️
A vector store always returns k results. There is no "nothing matched" — the bottom of your result list is noise with a score attached. Threshold it, rerank it, or grade it (Chapter 11).

📎 Citations for free

      
Because you already have the source documents, you can attach sources to the answer without asking the model to invent them:

      
chain = RunnableParallel(
    context=retriever,
    question=RunnablePassthrough(),
).assign(
    answer=(
        RunnableLambda(lambda x: {
            "context": format_docs(x["context"]),
            "question": x["question"]})
        | prompt | model | StrOutputParser()
    )
)

out = chain.invoke("Can I deploy on a Friday?")
out["answer"]                       # the text
[d.metadata["source"] for d in out["context"]]

      
.assign() adds a key while keeping everything already in the dict — which is how the documents survive alongside the answer.

    

  

  









  

    
Chapter 9 · Stateful

    
The model remembers nothing

    
"Memory" in LangChain means: store the messages, load them by session id, splice them into the prompt before the next call. That is all. Understanding this makes both the privacy bug and the cost curve obvious in advance.

💻 Wiring it up

      
from langchain_core.runnables.history import (
    RunnableWithMessageHistory)
from langchain_core.chat_history import (
    InMemoryChatMessageHistory)

store = {}
def get_history(session_id: str):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

chat = RunnableWithMessageHistory(
    chain, get_history,
    input_messages_key="question",
    history_messages_key="history",
)

chat.invoke(
    {"question": "And the week before?"},
    config={"configurable": {"session_id": "alice"}},
)

      
InMemoryChatMessageHistory is for demos. Swap in Redis, Postgres or a LangGraph checkpointer the moment there are two processes.

A loop that decides its own next step

Chapter 11 · Stateful

    
When a chain needs to go backwards

    
LCEL builds a DAG: data flows forward and never loops. But "retrieve, check whether it was any good, and try a different query if not" is a cycle. LangGraph gives you explicit state, real cycles, checkpoints you can resume from, and interrupts for human approval.

📌 Why bother

    

  


  

    
🖐️

    
Human in the loop, concretely. Compile with interrupt_before=["execute"] and a checkpointer. The graph runs up to that node, stops, and hands you the full state. Approve it, edit a value, or reject — then call app.invoke(None, config) to resume from exactly where it paused. Building that yourself over an LCEL chain is not a small job.

Chapter 12 · Shipping

    
Tracing, cost, and the debugging order

    
LangChain is a library, not a runtime — you deploy it inside whatever you already have. What changes in production is that you can no longer see what the chain did, which is why tracing is the first thing to turn on, not the last.

  


  

    
🏛️ The pieces

    

  


  

    

      
🔍 Turning on tracing

      
export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY=...
export LANGSMITH_PROJECT=northwind-support

      
That is the whole integration — every runnable already emits callback events, so every step of every run shows up with its inputs, outputs, token counts, latency and errors. Name your steps so the trace is readable:

      
chain = (
    retriever.with_config(run_name="retrieve")
    | format_docs
    | prompt
    | model.with_config(run_name="answer")
    | StrOutputParser()
)
