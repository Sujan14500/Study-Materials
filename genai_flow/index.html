Chapter 1 · Foundations

Software that guesses instead of following orders

Traditional code does exactly what you wrote. A generative model does what its training makes most likely. That one difference explains almost everything that follows — the magic and the failure modes.

1970s →

Rules

A human writes every condition by hand.

if word == "hola":
    return "hello"
PredictableBrittle
2000s →

Classic ML

You show labelled examples; it learns to classify.

model.fit(emails, ["spam","ok"])
model.predict(new_email)
# -> "spam"
Learns patternsFixed menu of answers
2020s →

Generative AI

Learns from oceans of text; creates new output, one piece at a time.

llm("write a haiku about spam")
# -> three original lines
Open-endedProbabilistic

🎮 Try it: be the language model

interactive

A model has exactly one job: predict what comes next. Play a round — pick the word you think is most likely, then see what a model would have said.

💡
The whole trick. Predict the next piece of text, over and over, extremely well. Do that at enough scale and it looks like reasoning, translation, coding and conversation — because all of those are text that follows text.

Take away

  • Rules → you encode the logic. ML → it learns the boundary. GenAI → it generates new content.
  • The model isn't looking anything up. It produces the most plausible continuation.
  • Plausible ≠ true. Grounding, RAG and evals all exist because of that gap.
Chapter 2 · Foundations

Models don't read words. They read tokens.

Before anything else happens, your text is chopped into chunks called tokens, and each chunk becomes a number. Tokens are the unit of cost, the unit of speed, and the unit of the context limit. Get comfortable here and half of GenAI stops being mysterious.

✂️ Live tokenizer

interactive

Type anything. Watch it split. Notice how common words are a single token, rare words shatter into pieces, and the leading space belongs to the token.

📏 Rules of thumb

  • 1 token ≈ 4 characters of English
  • 1 token ≈ ¾ of a word → 100 tokens ≈ 75 words
  • A page of prose ≈ 500 tokens
  • Code and non-English text burn more tokens per idea
  • You pay for input tokens and output tokens

🧨 Why this bites people

  • "Count the r's in strawberry" is hard because the model never sees letters — it sees str · aw · berry.
  • Rhyming and spelling puzzles are tokenizer problems, not intelligence problems.
  • A 200-page PDF won't fit in context. That's a token budget problem, and it's exactly why RAG exists (Chapter 10).
  • Non-English languages can cost 2–3× more tokens for the same sentence.
🔤
Token → ID → vector. "cat" might be token #4937. That number is only an address; the meaning lives in the vector it points to. That's the next chapter.
Chapter 3 · Foundations

Meaning as coordinates

Every token becomes a long list of numbers — a vector. Similar meanings land near each other. That's the whole idea, and it powers semantic search, recommendations, RAG, and the model's own sense of what words mean.

🗺️ The meaning map

interactive

Real embeddings have hundreds or thousands of dimensions. Here is a hand-built 2D version so you can see the shape of it. Pick a word to find its nearest neighbours.

➕ Vector arithmetic

interactive

The famous one. Directions in the space carry meaning — there's a "royalty" direction and a "gender" direction. Run it and watch the arrows.

📐 Cosine similarity

How "near" gets measured: the angle between two vectors, not the distance. 1.0 = same direction, 0 = unrelated, −1 = opposite.

sim(a, b) = (a · b) / (|a| · |b|)

sim("dog", "puppy")     -> 0.86
sim("dog", "database")  -> 0.07

🎯 Where you'll use this

  • Semantic search — "how do I cancel" finds "subscription termination"
  • RAG retrieval — pick the right paragraphs to feed the model
  • Clustering — group support tickets nobody labelled
  • Dedup & recommendations — near neighbours are near-duplicates
Chapter 4 · Inside the model

Attention: every word looks at every other word

The 2017 idea that unlocked all of this. When the model processes a word, it decides how much every other word matters for understanding it. "It" looks back and finds what "it" refers to — and nobody wrote a rule for that. It was learned.

👁️ Attention explorer

interactive

Pick a sentence, then hover or tap a word. Line brightness = how strongly that word attends to each other word.

🏗️ One transformer block, animated

Stack this block 30–100 times and you have a modern LLM. Each pass refines the meaning of every token using its neighbours.

1Embedtokens → vectors
2+ Positionorder gets encoded
3Self-attentiontokens mix context
4Feed-forwardthink about it
5× N layersrepeat, deepen
6Predictscore every token
⚡
Why it scaled. Attention compares all tokens at once instead of reading strictly left to right like older RNNs. Parallel = GPU-friendly = you can train on the internet. The cost: work grows with the square of the sequence length, which is why long context is expensive.
Chapter 5 · Inside the model

Watch it write, one token at a time

The model outputs a probability for every token in its vocabulary. Something picks one. That pick is appended to the input and the whole thing runs again. Temperature and top-p control how the pick is made — the knob people most often get wrong.

🎲 The sampler

interactive

Step through generation and watch the candidate distribution reshape as you move the sliders.

Only consider the smallest set of top tokens whose probabilities add up to p. Greyed-out bars are cut.

temp = 0

Always the top token. Repeatable, safe, dull. Use for extraction, classification, JSON output.

temp ≈ 0.7

The default sweet spot. Natural writing, still coherent.

temp > 1.2

Chaos. Brainstorming and poetry — or word salad. Rarely what you want in production.

🧠
Hallucination lives here. There is no highly-weighted "I don't know" token by default — only "the most plausible next word". Fluent and wrong is the natural failure mode, not a bug you can fix with a stern prompt alone.
Chapter 6 · Inside the model

From raw internet to helpful assistant

A base model trained on raw text is a very good autocomplete and a terrible assistant. Three stages turn one into the other. Click through them.

💸 What it costs

  • Pretraining a frontier model: thousands of GPUs, months, $10M–$1B+
  • Fine-tuning an existing model: hours to days, $10–$10k
  • Prompting: free, instant, right now

This is why 99% of teams never train a model. You start at the cheap end and only move left when you have proof you must.

🧬 Vocabulary you'll hear

Parameters
The learned numbers. "70B" = 70 billion of them. More ≈ more capable and more expensive.
Base model
Pretrained only. Completes text; doesn't follow instructions.
Instruct / chat model
Base + SFT + preference tuning. What you actually call.
Open weights
You can download and run it yourself (Llama, Mistral, Qwen…).
Reasoning model
Trained to spend extra tokens thinking before answering.

📚 Techniques worth knowing

    

  


  

    
⚠️

    
Prompt injection. The moment your prompt includes text from users, web pages or files, that text can try to give the model instructions. Never let retrieved content carry authority — keep instructions and data clearly separated, and never wire an untrusted string straight into a tool that can spend money or delete things.

  









  

    
Chapter 8 · Building with it

    
The model has no memory

    
Every API call is a fresh brain with amnesia. "Conversation" is an illusion created by resending the entire chat history each turn. Everything you resend has to fit in the context window — and you pay for it every single turn.

🧯 When context runs out

      
    
        
  • Truncate — drop the oldest turns. Cheap, and it forgets.
    • 
        
  • Summarise — compress old turns into a paragraph. Keeps the gist.
    • 
        
  • Retrieve — store everything outside, pull back only what's relevant. That's RAG.
    • 
        
  • Structured memory — write facts to a database, inject the ones that matter.
    • 
      

    

    

      
🕳️ "Lost in the middle"

      
Big context windows are not a free pass. Models reliably attend to the start and the end of a long input and get hazy in the middle.

      

      
Put the instruction last, the critical facts first, and don't dump 200 pages when 3 paragraphs would do.

    

  









  

    
Chapter 9 · Building with it

    
RAG: give the model an open book

    
Retrieval-Augmented Generation. The model doesn't know your company's refund policy and never will. So don't ask it to remember — look the policy up first and paste it into the prompt. This is the single most common GenAI architecture in production.

🩺 When RAG goes wrong

      
    
        
  • Bad chunking — the answer got split across two chunks. Most common cause.
    • 
        
  • Vector-only search — misses exact IDs, error codes, names. Combine with keyword search (hybrid).
    • 
        
  • No reranker — top-k by cosine is rough; a reranker re-sorts by real relevance.
    • 
        
  • Stale index — the doc changed, the vector didn't.
    • 
        
  • No citations — you can't debug what you can't trace.
    • 
      

    

  


  

    
🎯

    
Retrieval quality is the product. If the right chunk isn't retrieved, no model and no prompt can save the answer. Debug retrieval before you blame the LLM.

Chapter 11 · Building with it

    
Give it hands

    
A chat model only produces text. An agent is that same model in a loop, allowed to call tools — search, a database, an API, your codebase — look at the results, and decide what to do next. Same brain, plus the ability to act and check its work.

🧰 What a tool actually is

      
A JSON description of a function. The model doesn't run it — it emits a request, your code runs it and hands back the result.

      
{
  "name": "get_weather",
  "description": "Current weather for a city",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {"type": "string"}
    },
    "required": ["city"]
  }
}

    

    

      
🚧 Agents in the real world

      
    
        
  • Errors compound: 95% per step is 60% over 10 steps.
    • 
        
  • Cap the loop. Always. Runaway agents burn money fast.
    • 
        
  • Keep dangerous tools behind human approval (deletes, payments, sends).
    • 
        
  • Fewer, sharper tools beat thirty vague ones.
    • 
        
  • Log every step — an agent you can't replay is an agent you can't fix.

Chapter 12 · Shipping it

    
How do you know it's any good?

    
"It looked great in the demo" is not a quality bar. The same input can produce a different output every run, so you need evaluation the way normal software needs tests — otherwise every prompt tweak is a coin flip.

  


  

    
🕵️ Spot the hallucination
interactive

    
Each answer sounds confident. Click the part you think is invented.

    

  


  

    

      
📊 Ways to measure

      

        
Golden set
30–200 real inputs with known-good answers. Run them on every change. This is 80% of the value.

        
LLM-as-judge
A model grades outputs against a rubric. Scales well; calibrate it against humans first.

        
Exact / structural checks
Valid JSON? Schema matches? Citation actually exists? Cheap and deterministic — do these first.

        
Human review
Slow, expensive, still the ground truth. Sample it continuously.

        
Online signals
Thumbs, edits, escalations to a human, retry rate.

      

    

    

      
🛡️ Risks to design around

      
    
        
  • Hallucination → ground with RAG, demand citations, allow "I don't know".
    • 
        
  • Prompt injection → separate instructions from data, never auto-run destructive tools.
    • 
        
  • Data leakage → redact PII before it leaves your systems; know your provider's retention.
    • 
        
  • Bias → training data carries the world's biases; test across groups.
    • 
        
  • Silent regressions → pin model versions, re-run evals when you upgrade.
    • 
        
  • Over-trust → show sources, show uncertainty, keep a human on high-stakes calls.
