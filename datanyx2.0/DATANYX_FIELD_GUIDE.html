Two execution paths from one endpoint. When the caller supplies datasourceDetails, the agent connects to the source database itself and returns rows plus a chart. When it doesn't, the agent returns only the SQL/spec and the BI app executes it — which preserves row- and column-level security, and is also the graceful fallback when the agent cannot reach the source DB.

Why one Flask app hosts two services

The Angular frontend already targeted one host and port. api.py at the repo root is a composition root: it boots sqlService routes inline and mounts agentService as a Blueprint at /agent/* on port 5000. It configures logging once with force=True (several imported modules call basicConfig themselves), and chdirs into sqlService/ because that service reads config relative to cwd while agentService resolves its own by absolute path. The same Blueprint object serves the standalone port-5001 app, so the two modes cannot drift.

Three modelling decisions worth naming

  • Soft deletes everywhere. A re-detected category, topic or dashboard keeps its original id, so saved artifacts keep resolving.
  • Python attributes decoupled from physical columns via Column("db_name", …) — the DB could be renamed without touching application code.
  • Embeddings written twice during migration. The legacy JSON-float TEXT column is still written for back-compat but no longer read; retrieval runs natively over pgvector.

Onboarding pipeline 11 stages · checkpointed · resumable

Triggered by POST /agent/connect, run on a background thread pool. Status flows pending → introspecting → ready; /ask returns HTTP 409 until ready.

  1. connect Read-only SQLAlchemy connection to the source DB.
  2. introspect Tables, views, columns, types, PKs, declared FKs, constraints, row-count estimates.
  3. profile Per-column stats and PII/financial/health tagging. Parallelized, and publishes live intra-stage progress {done, total} so the progress bar moves within the stage while hundreds of tables are profiled.
  4. fk_inference Infers undeclared foreign keys from four signal families.
  5. role_classify Batched LLM labels each table's role and business domain, with heuristic fallback; a separate classifier assigns the connection's industry.
  6. vector_embed Builds a natural-language summary per table and embeds it.
  7. glossary_bootstrap Tool-calling agent mines business terms from schema and real data.
  8. category_generate AI invents dashboard categories and up to three templates each.
  9. dashboard_build Agentic KPI proposer builds the starter dashboard.
  10. report_topics AI generates narrative-report topics with structural blueprints.
  11. plan_snapshot_build Pre-computes window-independent report plans so report generation later skips retrieval and planning LLM calls.

Resumability. Each stage writes last_completed_stage; a re-entered run skips everything at or before it, and unknown stage names are defensively treated as not-done. POST /refresh clears the checkpoint. A startup sweep bounces rows stuck in INTROSPECTING for over 30 minutes — a dead worker, a container OOM — back to PENDING; the same pattern covers stale dashboards and document ingestions.

Foreign-key inference — LLM proposes, code disposes

Four signals merge: a name heuristic (<thing>_id → table resembling <thing> above 0.6 similarity), shared normalized key names with an orientation decision, value-shape agreement, and optional LLM proposals for pairs the textual heuristic misses — the classic purchaser_id → customers.id.

LLM proposals are never trusted alone. They pass a deterministic value-overlap gate that samples both columns from the live database and requires real overlap before the edge is persisted. Every stored edge carries its source, origin tag and confidence.

Why a structured spec instead of raw SQL

The shipped path does not have the LLM write final SQL. It emits a validated JSON spec that the Node BI report generator compiles and executes. Three reasons:

  • Security. SQL is generated by deterministic, already-audited BI code, and execution runs the same path dashboards use — so row- and column-level security are preserved without being reimplemented.
  • Correctness. A spec is checkable field-by-field against the catalog before anything executes: does this column exist on this table, is this aggregation legal, is this join reachable.
  • Capability honesty. When a question needs something the generator cannot express, the synth raises UnsupportedQuestionError instead of silently producing something wrong.

The response envelope

Every answer — success or failure, on every path — is built from one skeleton, so a key is never missing. Builders only overwrite blocks, never delete them, which makes totality structural rather than a per-call discipline. schemaVersion is currently 3; v3 is when charts moved from base64 PNG to live React components.

  "status": "success",

  "queryId", "traceId", "durationMs", "message", "question",

  "followup":     { isFollowup, rewrittenQuestion },

  "links":        { feedbackUrl, inspectHtmlUrl, clarifyEndpoint },
  "payload":      { intent, result, chart }
}

transparency is the trust surface. A text-to-SQL system's worst failure is not being wrong — it is being wrong invisibly. If the agent assumed "revenue" meant net_amount, that assumption ships next to the number.

The retrieval algorithm Vector search was 60% of it

What gets embedded is not DDL. Each table gets a natural-language summary — name, LLM-assigned role, business domain, description, column names with types and representative samples — and that is embedded. User questions are in business language, so a summary reading "sales fact table, domain commerce, columns include order_date, net_amount, customer_id" sits far closer to "how much did we sell last month" than CREATE TABLE sls_hdr does.

  1. Embed the question (cached) and run pgvector top-k, DEFAULT_TOP_K_TABLES = 12.
  2. Near-duplicate suppression. Two tables whose column-name sets overlap ≥ 0.70 collapse to the higher-ranked one. Denominator is max(len(a), len(b)), so a small lookup dim inside a wide fact is not flagged. Shown both, the LLM joins them and selects duplicate columns — which fails at execution with ER_DUP_FIELDNAME under MySQL's case-insensitive matching.
  3. Deprecated-twin tiebreak. When the duplicate pair differs only by _old / _bak / _archive, the canonical name wins regardless of rank — a 0.004 cosine gap must not strand every column the LLM will reference.
  4. FK-graph expansion. Vector similarity is blind to the FK graph, so 1-hop neighbours of the seed tables are pulled in (capped) — otherwise the fact table arrives without its dimensions and a fully-supported join becomes impossible.
  5. Relevance floor at 0.30 cosine. Vector search essentially never returns zero rows, so an off-topic prompt still retrieved something and got a confident fabricated answer. Observed: real topics ~0.4+, noise ~0.11–0.19.
  6. Metric-source augmentation. Tables a bound glossary metric depends on are force-added even when vector search missed them.

Glossary retrieval is exact-match-first, not cosine-first

If a user literally names a metric — "show me GMV" — that definition must be injected; leaving it to cosine risks the right term ranking ninth and being dropped. So the order is: exact term or alias match, then fuzzy name match (trigram similarity plus Damerau–Levenshtein for typos), then cosine for concepts the user described rather than named, then dependency closure via depends_on so a ratio's numerator and denominator come along. The cap is a token budget of 4000 rather than a fixed top-k, with 1500 reserved for cosine hits so exact matches cannot starve them. Human-confirmed terms get a +0.10 rank boost, human-authored +0.05, so curated entries outrank equally-similar LLM drafts.

Sub-agents and capabilities

Glossary agent — the semantic layer

A tool-calling agent with list_tables, describe_table, get_distinct_values, sample_rows and finalize_term — so it can look at real data before naming a concept. It proposes seven term types: acronym, filter, metric, dimension, entity, synonym, and join_path. Every SQL-bearing fragment passes a deny-token check; every term is stored as proposed with a confidence score until a human confirms it.

Conversational editing is the part users feel. Someone says "active customer should only count people who ordered in the last 90 days"; the service translates that into a structured recipe change, shows an old→new diff, and applies it only on confirm. Terms are versioned and revertible. There are also ad-hoc terms scoped to "this chat only". The pipeline deliberately does not cache the agent's catalog bindings across turns, precisely so an edit takes effect on the very next question.

KPI / dashboard agent

The agent explores the live database through tools and emits finalized KPI SQL with real names. The runner then re-executes every KPI itself under a row cap and statement timeout so a model-written query cannot wedge the service, asks the chart picker for a Vega-Lite spec derived from the actual result shape, and persists KPI, value and chart. There is deliberately no template fallback — "if the LLM is down, no dashboard" — because a generic template dashboard looks authoritative while being disconnected from the customer's schema.

Narrative report agent

The largest sub-package, around 10k lines. It produces multi-section HTML/React reports honouring topic, time period, comparison window and section choices. The mechanics that matter: the selected window is translated into the BI app's filterObj and threaded through every query, so totals reflect the window rather than cached all-time KPI values; "compare against" re-runs the same queries over the prior window for period-over-period deltas; KPIs carrying structured metadata are re-measured under the window with their own row-scope filter, so a subset KPI can never come out larger than its parent total. Quality gates include a coverage critic, a prose guard, evidence and ranking passes, and an audience inference that is cached alongside the plan snapshot. Everything is best-effort — a failing sub-question is logged and skipped so the report still composes.

Visualization agent

One LLM call returns the best chart, ranked alternatives for the UI dropdown, and the caption. It never raises — any failure falls back to a table plan. A high-cardinality guard downgrades a bar chart over 500 categories. Charts render as data-driven React/Recharts components; the legacy deterministic Vega-Lite path still serves dashboard tiles.

Document agent — RAG over uploaded files

Read → understand → embed → route, mirroring onboarding: one background job per document, resumable via a checkpoint, per-document failure isolation, SHA-256 dedupe per connection. Bytes live in S3 — the BI app uploads and hands over the key, the agent only reads. Scanned, text-empty PDFs are rasterized with PyMuPDF and read by the vision model, chosen over pdf2image specifically because it needs no poppler binary. Chunks carry a source locator ({"page": 3}) so answers can cite them. An FK asserted by an ER diagram still has to pass live probe verification, or it parks in pending_proposals for human confirmation.

Questionnaire — "AI Setup"

Three tiers capturing what the AI genuinely cannot infer. Common questions (fiscal year start, week start, timezone) live in global YAML. Domain banks are selected by function and industry. Schema questions are generated per connection from the catalog, LLM-phrased, cached, and regenerated only when a catalog hash drifts — never per page open, because the phrasing pass is the expensive part. Only answers are stored per connection; answers emit real artifacts and the row points at what it emitted, so an edit rewrites that artifact rather than creating a second one. Org-common answers are shared across a tenant, with precedence per-source > org-common > standard default.

Safety & governance

The sqlglot safety gate, in order

  1. Reject empty SQL.
  2. Forbidden-substring scan: into outfile, load_file(, xp_cmdshell, sp_executesql, pg_sleep(, benchmark(, sleep(.
  3. Parse with sqlglot at the target dialect.
  4. Top-level node must be Select, With, or a set operation.
  5. Walk the whole tree rejecting Insert/Update/Delete/Create/Drop/Alter/Truncate/Merge/raw Command nodes anywhere, including nested.
  6. Table allow-list drawn from the retrieved slice.
  7. Column-existence check with alias and CTE-alias resolution; unqualified columns must exist on at least one FROM/JOIN table, not merely somewhere in the slice.
  8. PII-in-projection check.
  9. Inject a dialect-correct row cap (1000) when no LIMIT is present — including T-SQL TOP wrapping for set operations.

Why bother when the role is read-only? Read-only is a deployment claim you cannot verify at runtime, and it stops neither exfiltration primitives (INTO OUTFILE, load_file()) nor resource exhaustion (SELECT * with no LIMIT, benchmark() as a DoS).

The parse-failure trade-off, stated explicitly

sqlglot is an incomplete parser for some dialects — ClickHouse especially, where function-arity validation trips on valid nested duration math. Hard-rejecting there killed valid queries after the entire repair budget was spent, and the model cannot "fix" SQL that was never wrong. So a parse failure falls back to AST-free checks: no chained statements, must begin SELECT/WITH, append a row cap — and lets the source DB, the real authority on its own dialect, validate the rest.

The exception is the point: it fails closed when the schema has PII columns, because PII safety cannot be proven without an AST. Degrade availability for unparseable SQL; never degrade confidentiality.

PII, tenancy, and what is deliberately not stored

  • Columns tagged pii/financial/health may appear in WHERE, JOIN and GROUP BY — those filter rows — but never raw in the SELECT projection unless wrapped in an aggregate. Alias resolution means u.email is recognized as users.email.
  • Tenancy has three layers: the 4-tuple identity with unique constraints and ambiguity rejection; explicit tenant + user authorization returning 403; and execution through the BI app with user/client headers so its own RLS applies. RLS is routed to, never reimplemented.
  • Chat history stores no raw result rows — only question, answer text, SQL and the spec. Reopening replays the spec through the RLS path, so a user who lost access to rows since the original answer does not see them on reload.
  • Secrets may be committed encrypted with a ~ marker and are decrypted at read; sensitive datasource fields are redacted in logs.

Reliability engineering

  • Checkpoint and resume on both onboarding and document ingestion; unknown checkpoint values re-run defensively.
  • Startup sweeps for stuck introspections (30 min), stale building dashboards, and stale document jobs.
  • Fail-open where it is safe: router errors → data path; glossary errors → empty enrichment; audit store unreachable → non-fatal, because it must never block API serving.
  • Graceful degradation of execution: unreachable source DB → return spec only and let the BI app run it.
  • 0 rows is a soft signal. Retry once, then return the 0-row result as a legitimate answer rather than an error.
  • The Werkzeug reloader is off by default — the watchdog would kill long-lived onboarding threads and a double import would create two thread pools.
  • Layered config with provenance logging — four layers, later wins, and boot logs show which file won each key.

Known gaps worth naming before an interviewer finds them

The audit/query log is currently a documented no-op since the ClickHouse store was removed, which means few-shot example selection and glossary mining have no history to draw on. sqlService has no automated tests. Caches are per-process, so multi-instance deployment lowers hit rate. The EXPLAIN dry-run helper is built but deliberately not wired into /ask pending a latency-versus-value call. There are token budgets but no per-tenant spend ceiling yet.

A · Project story Part two · 50 questions

Each question is collapsed so you can quiz yourself. The SAY line is what you answer out loud; the rest is for the follow-up that always comes.

Q01Tell me about this project in two minutes.

SayA GenAI backend that turns any customer database into a conversational BI system.

Two halves. The legacy half, sqlService, is a LangChain text-to-SQL engine. The half I'll focus on, agentService, is an autonomous database-analysis agent: give it read-only credentials and it onboards itself — introspects the schema, profiles every column, infers foreign keys that were never declared, uses an LLM to classify each table's role and business domain, mines a business glossary, embeds everything into a pgvector index, and generates a starter KPI dashboard and report topics.

After that, users ask questions in English. The agent retrieves the relevant schema slice by vector search, synthesizes a validated structured analytics spec, executes it through the BI platform's row-level-security engine, picks a chart, writes a caption, and returns a versioned response envelope. About 75,000 lines across 253 modules, 67 endpoints, 94 test files.

Q02What was the hardest problem you solved?

SayMaking an LLM behave correctly on schemas far too large to fit in a prompt, without letting it hallucinate.

Three sub-problems, each with a concrete fix. Schema size — solved with RAG: every table gets an LLM-readable summary, embedded to 1536 dims, retrieved top-12 by pgvector cosine. Retrieval alone isn't enough — vector search is blind to the FK graph, so the fact table arrived without its dimensions and a supported join became impossible; fixed by expanding the slice with 1-hop FK neighbours. Silent fabrication — vector search essentially never returns zero rows, so an off-topic question still retrieved something and got a confident answer; fixed with an empirical relevance floor at 0.30 cosine. Real topics score ~0.4+, noise ~0.11–0.19.

Q03What would you do differently if you rebuilt it?

Four things. Move background jobs off an in-process thread pool onto a real queue earlier — checkpoints and sweeps work, but they are compensating controls. Make the caches shared rather than per-process, because horizontal scaling silently drops the hit rate. Add per-tenant cost ceilings from day one; we have per-prompt token budgets but no spend ceiling. And build the evaluation harness before the features — 94 contract and unit test files prove the pipeline holds its shape, but a golden-question set scored on answer correctness would catch prompt regressions faster.

Q04What's the single most important architectural decision?

SayThe LLM does not write the final SQL on the main path.

It emits a structured JSON spec — dimensions, measures, joins, filters, having, sort, custom columns — validated field-by-field against the catalog and POSTed to the BI platform's report generator, which compiles and executes it. Three payoffs: row/column security is enforced by existing audited code instead of reimplemented; the spec is machine-checkable in a way free SQL isn't; and when a question needs something the generator can't express, we raise UnsupportedQuestionError and say so instead of shipping plausible-but-wrong SQL.

Q05Who are the users and what does success look like?

Business users inside a customer's organisation — people who know the business but not SQL. Success is: the agent onboards a new datasource unattended; a first question gets a correct, charted answer with nobody writing SQL; and when the agent is unsure it says so — clarification, transparency block, confidence label — rather than guessing. That last part is why so much of the code is refusal and transparency logic rather than generation.

Q06How is this different from calling ChatGPT with a schema?

Five differences, all load-bearing in production. Schemas don't fit in context — hence RAG. Real column names carry no business meaning — hence the glossary and profiling. FKs are often undeclared — hence inference with value-overlap verification. Multi-tenant SaaS needs RLS and PII controls — hence spec execution through the BI engine and the AST PII guard. And an LLM answering confidently on a schema it misread is worse than no answer — hence the relevance floor, confidence scoring, and the clarification path.

B · Architecture

Q07Walk me through the request flow of one question.
  1. POST /agent/ask or /ask/stream. Validation decodes base64 datasourceDetails, resolves dataSourceId to the internal connection via the identity tuple, and enforces tenant + user ownership.
  2. Router — one JSON-mode LLM call decides follow-up-and-rewrite plus intent across nine buckets.
  3. Intent dispatch — metadata, report, refine, correction, conversational, unsupported, out-of-scope and clarify all short-circuit here.
  4. Data path — retrieve slice + glossary + relationships with no LLM, one structured-synth call, execute via Node, bounded repair on error or 0 rows.
  5. Tail — one chart call producing chart + alternatives + caption, confidence score, assumptions and ambiguities, audit record, response envelope.
Q08Why is connection identity a 4-tuple instead of just dataSourceId?

Because the numeric datasource id is not unique across the system — the same id exists in different environments and can belong to different tenants and users. Keying on it alone would let one tenant's question resolve to another tenant's catalog row. Identity is (tenant_id, user_id, data_source_id, env_name), enforced by two unique constraints, and endpoints reject an ambiguous lookup rather than picking one. /ask returns 403 on ownership mismatch.

Q09Why two datastores, and why is neither the source database?

The catalog DB (Postgres + pgvector) is the agent's own memory: connections, tables, columns, profiles, FKs, glossary, KPIs, dashboards, reports, conversations, embeddings. It must be separate from the customer's database because we only have read-only access there and must not write to it. The second store was ClickHouse for the audit/query log — deliberately separate because a high-volume append-only log has different characteristics from transactional catalog data, and because an unreachable log must never block API serving. That store has since been removed, so the audit module is a documented no-op that still mints query ids so every downstream artifact keeps working.

Q10Why did you mount two services in one Flask app?

Product constraint — the Angular frontend already hit one host and port. api.py is a composition root that boots sqlService routes inline and agentService as a Blueprint at /agent/* on port 5000. It configures logging once with force=True because several imported modules call basicConfig themselves, puts both service directories on sys.path, and chdirs into sqlService/ since that service reads config relative to cwd while agentService resolves its own by absolute path. The same Blueprint object serves the standalone port-5001 app, so the two deployment modes can't drift.

Q11How does the agent talk to six different database engines?

SQLAlchemy with per-engine dialects across MySQL, PostgreSQL, SQL Server, Oracle, Databricks and ClickHouse. Two documented hacks: oracledb is aliased into sys.modules as cx_Oracle (cx_Oracle doesn't build on modern setuptools and SQLAlchemy imports it lazily), and the ClickHouse dialect is patched for SQLAlchemy 2.0. Dialect-specific generation goes through sqlglot, and the exact server version captured at onboarding is named in the synth prompt so the model avoids features the engine lacks — CTEs on MySQL 5.x, FETCH FIRST on Oracle 11g.

Q12Why a fixed response envelope with a schema version?

Because the original code hand-assembled eight different dict literals across the orchestrator, and fields the frontend treated as always-present were silently missing on error paths — the same kind: "answer" even shipped results two different ways. Now every response starts from one skeleton and builders only overwrite blocks, never delete keys, so totality is structural rather than a per-call discipline. schemaVersion, currently 3, lets the frontend detect a breaking change and warn instead of crashing; v3 is when charts went from base64 PNG to live React components.

Q13What is the transparency block and why does it exist?

It carries tablesUsed, assumptions, ambiguities and clarificationsOffered on every answer. It exists because a text-to-SQL system's biggest failure isn't being wrong — it's being wrong invisibly. If the agent assumed "revenue" meant net_amount rather than gross_amount, the user needs that assumption next to the number. It's also how the glossary grows: an ambiguity surfaced here becomes a clarification, and a confirmed clarification becomes a persisted term.

Q14Where does state live in a conversation?

Two places only. Durable state in agent_conversation/agent_message: question, answer text, generated SQL, and the chart and dim-measure specs — but not raw result rows, for PHI safety. On reload, the render endpoint replays the spec through the RLS-preserving path to regenerate rows. Ephemeral state is a per-conversation in-memory store for "use this definition for this chat only" terms. Everything else is stateless, because the router rewrites follow-ups into standalone questions.

C · RAG, embeddings, retrieval

Q15What exactly do you embed?

Not raw DDL. For each table a summariser builds a natural-language description combining the table name, its LLM-assigned role and business domain, its description, and its column names with types and representative sample values. That summary gets embedded. Glossary terms and document chunks are embedded separately with the same model.

Why summaries beat DDL: user questions are in business language. "Sales fact table, domain commerce, columns include order_date, net_amount, customer_id" is semantically far closer to "how much did we sell last month" than CREATE TABLE sls_hdr (...) is.

Q16Why pgvector instead of Pinecone, Weaviate or FAISS?

Operational simplicity plus consistency. The embeddings describe metadata that already lives in Postgres, so keeping the vector in the same row as the table it describes means one datastore, one backup, one transaction, and no sync job that can drift. Search uses the native <=> operator through SQLAlchemy's Vector.cosine_distance backed by HNSW, so ranking and top-k happen inside Postgres — no per-question Python scan. The trade-off is sharing Postgres' availability and scaling envelope, which is fine at our catalog sizes.

Q17Walk me through retrieval, including the parts that aren't vector search.
  1. Embed the question (cached) and run pgvector top-12.
  2. Near-duplicate suppression at ≥0.70 column-name overlap, denominator max(len(a), len(b)) so a small lookup dim inside a wide fact isn't flagged. Showing both makes the LLM join them and emit duplicate columns — ER_DUP_FIELDNAME under MySQL's case-insensitive matching.
  3. Deprecated-twin tiebreak — _old/_bak/_archive loses to the canonical name regardless of rank, because a 0.004 cosine gap would strand every column the LLM references.
  4. FK-graph expansion — pull in capped 1-hop neighbours so the relationships block has in-slice edges.
  5. Relevance floor at 0.30 — refuse rather than answer.
  6. Metric-source augmentation — force-add tables a bound glossary metric depends on.

The point worth landing: pure vector search was about 60% of the solution; the deterministic post-processing around it made it production-usable.

Q18You cache embeddings — isn't caching risky for correctness?

Not for query embeddings, which is exactly why only those are cached. An embedding is a deterministic pure function of (text, deployment) — the same text always yields the same vector, like a hash. A cache hit is byte-identical to recomputing, so it can never introduce a wrong result. It's a 512-entry LRU keyed by (sha256(text), deployment), so a model change auto-misses, and only successful non-empty vectors are stored. It's pre-warmed at startup with recurring report topics so the first report after a restart doesn't pay a rate-limited round trip.

The question cache is different — question to schema slice isn't provably deterministic across schema changes, so it gets a 300-second TTL, a 256-entry bound, and explicit invalidation on refresh.

Q19How does glossary retrieval differ from schema retrieval?

Schema retrieval is cosine-first; glossary retrieval is exact-match-first, because the failure modes differ. If a user literally names a metric, that definition must be injected — leaving it to cosine risks the right term ranking ninth and being dropped. Order: exact term/alias match, fuzzy name match (trigram + Damerau–Levenshtein for typos), cosine for described concepts, then dependency closure via depends_on so a ratio's numerator and denominator come along. The cap is a 4000-token budget rather than a fixed top-k, with 1500 reserved for cosine hits so exact matches can't starve them. Human-confirmed terms get +0.10 rank boost, human-authored +0.05.

Q20How do you keep the prompt from exploding?

Named budgets everywhere, and tests that guard them. Glossary 4000 tokens; few-shot 2400 with k=3 from a pool of 100; metadata answers capped at 200 tables, 60 columns per table, 3 samples and 60,000 serialized characters; tool results row-capped at 8 for QA and 20 for KPI. In the agentic loop only the last three tool results are kept in full — earlier ones become short stubs. test_prompt_size.py and test_token_budgets.py fail the build if a change blows a budget.

Q21How does the document-upload RAG feature work?

Read → understand → embed → route, mirroring onboarding: one background job per document, resumable via a checkpoint, per-document failure isolation so one bad file doesn't fail a batch. Bytes live in S3 — the BI app uploads and hands over the key, the agent only reads. SHA-256 dedupes re-uploads per connection. Scanned, text-empty PDFs are rasterized with PyMuPDF and read by the vision model, chosen over pdf2image specifically because it needs no poppler binary. Chunks carry a source locator like {"page": 3} so answers cite them. In the route stage, an FK asserted by an ER diagram must still pass live probe verification or it parks in pending_proposals for human confirmation.

Q22Why do document chunks use JSON embeddings while tables use pgvector?

It's a migration in progress, and the code says so. Tables and glossary terms moved to native pgvector columns with an HNSW index; document chunks still use the older JSON-float-in-TEXT representation with cosine computed in Python. The legacy JSON column is still written for tables for backward compatibility but is no longer read by retrieval. Chunk volume per connection is small enough that the Python scan isn't the bottleneck yet — but it's the obvious next migration.

D · Prompting & LLM engineering

Q23Why does the router do two jobs in one LLM call?

Latency and consistency. Follow-up rewriting and intent classification need the same inputs — history plus the latest message — so splitting them meant two round-trips over nearly identical context. One JSON-mode call halves that latency and removes a class of inconsistency where the rewrite and the classification disagree about what the user meant. Same pattern in the chart picker: one call returns the best chart, the ranked alternatives for the dropdown, and the caption.

Q24What happens if the router's LLM call fails?

SayIt fails open — the user still gets an answer, never a 500.

Any failure — no LLM, malformed JSON, an intent outside the taxonomy, a routed intent missing required params — degrades to intent data, not-a-follow-up, original question. That's the general principle here: an enrichment step that fails should silently reduce quality, never break the request. Glossary retrieval, the relationships block and the audit write follow the same rule.

Q25How do you handle follow-up questions?

SayBy rewriting, not by context-stuffing.

The router turns "now just the top 5" into a standalone question carrying over only the subject, filter, time range and grouping the reference actually needs. Everything downstream — retrieval, glossary, few-shot, cache, synth — then works on a self-contained question with zero conversation awareness. The pipeline stays stateless and cacheable, and the retriever embeds a complete question rather than a fragment.

The prompt is explicit that sharing a topic is not a follow-up — the test is an unresolved reference: a pronoun, an ellipsis, or a request to modify the previous result. It's told never to carry over a filter the latest message didn't state, because that answers a different question than the user asked.

Related subtlety: the UI's "Select tables" scope is sticky across turns, so when a turn is not a follow-up we drop the inherited allow-list — otherwise a fresh unrelated question gets refused as irrelevant against the previous question's tables.

Q26How does the system know it can't answer something?

Three typed exceptions with three different user outcomes. IrrelevantQuestionError — the schema genuinely can't answer this. UnsupportedQuestionError — the question needs a construct the report generator can't express, such as some window functions, CTEs, UNION or self-joins. NeedsClarificationError — a named business term can't be grounded without guessing, so we ask a grounded question and the answer can be persisted as a real glossary term. Plus the router's terminal intents: conversational, unsupported (write/export/email/schedule — we're read-only), and out-of-scope general knowledge, which is never free-answered.

Q27Why is the clarification decision made in synth, not in the router?

Because the router has no schema visibility — it would be guessing. If a user names a term the dataset doesn't define, the router still routes to the data path; the schema-aware structured synth, which can see the actual columns and the retrieved glossary, decides whether the term can be grounded, and asks only when it genuinely can't. Router-level clarify is reserved for genuinely vague wording.

Q28Describe the self-repair loop.

Two nested loops, both bounded. Inner (catalog validation): the synth validates the spec against the catalog — column existence, legal aggregations, joinable tables, resolvable custom-column references, duplicate output names — and re-prompts with the specific problems. Outer (execution): the spec goes to Node; on an execution error or 0 rows the real failure text is appended and the spec re-synthesized, bounded at two attempts.

A 0-row result is a soft signal, usually a wrong filter value: retry once, but if the budget runs out return the 0-row result as a legitimate answer rather than failing. The re-synth threads the error through the existing "previous turn" free-text channel instead of forking the prompt builder — one less prompt to keep in sync.

Q29You said error messages are "engineered for the model". Explain.

Two concrete changes in the safety gate. Collect all failures in one pass. The original code rejected on the first unknown column; a wide report references ~40 columns across a dozen tables, so each repair fixed one column and the next attempt surfaced another — the repair budget was exhausted before the query was clean. Now every bad column is reported together with an instruction to fix them all in a single corrected query. Add "did you mean". Unknown names are matched against real catalog names with difflib.get_close_matches (n=3, cutoff 0.6) and echoed in the catalog's exact casing, since ClickHouse identifiers can be case-sensitive. Without it the model re-emits the same invented name.

The lessonA rejection message is a prompt. Optimize it like one.

Q30What temperature do you use and why?

0.0 almost everywhere — spec synthesis, chart picking, intent routing, role classification. These have correct answers, not creative ones, and determinism makes debugging and caching tractable. The one deliberate exception is the narrator at 0.2, which writes the one-sentence caption where variation reads better and there's no correctness risk. Max-token budgets are per task: 8000 for SQL synth, 700 for the router, 600 for the chart planner, 120 for the narrator.

Q31How do you handle different LLM model families?

Through a compatibility shim that rewrites temperature and max_tokens for families that reject them — newer reasoning models refuse a non-default temperature and renamed the token parameter. Wrapping that in one place made supporting a new GPT version a config change rather than an edit at every call site. On the sqlService side there are pluggable providers — Datanyx-default Azure OpenAI, a customer's Databricks serving endpoint, or a customer's own OpenAI key — with no silent fallback when a provider's credentials are missing, so traffic never quietly lands on the wrong model or the wrong bill.

E · Agents & tool calling

Q32Which parts are true agents versus a fixed pipeline, and why?

Three genuine tool-calling agents — glossary proposer, KPI proposer, FK proposer — all running at onboarding time, where a 30–60 iteration exploration loop is acceptable because it happens once. The main /ask path is a fixed pipeline with a single synth call plus bounded repairs, because the user is waiting and the earlier agentic version's variable iteration count made latency unpredictable. A true tool-calling QA loop still exists as a hybrid path.

The ruleAgentic where exploration is genuinely needed and latency is amortized; deterministic where the user is blocked.

Q33What tools does the glossary agent get, and what stops it inventing terms?

Tools: list_tables with role/domain/row count, describe_table, get_distinct_values for low-cardinality categoricals, sample_rows for up to five real rows, and finalize_term. So it can look at the data before naming a concept — it discovers status holds A/I/X and proposes an "active customer" filter grounded in the real value.

Guards: every SQL-bearing fragment passes a deny-token check, while term types carrying no SQL skip it as a no-op. Every term is stored as proposed, source llm, with a confidence score — visibly a draft until a human confirms — and confirmed terms get a retrieval rank boost so they outrank equally-similar drafts.

Q34How does FK inference work, and how do you avoid bad edges?

Four signal families: a name heuristic (<thing>_id → table resembling <thing>, similarity above 0.6), shared normalized key names with an orientation decision, value-shape agreement (UUID, numeric, prefixed code), and optional LLM proposals for semantically likely pairs the textual heuristic misses — purchaser_id → customers.id, where nothing about the strings suggests a relationship.

The critical part: LLM proposals pass through a filter that samples both columns from the live database and requires genuine value overlap before persisting. Every stored edge carries source (declared vs inferred), origin (heuristic vs llm) and confidence, so consumers can weight them.

Name the patternLLM proposes, deterministic code disposes — in FK inference, in spec validation, and in the document agent's FK proposals.

Q35How do you bound an agent loop so it can't run forever?

Three separate limits per loop, all named constants: a max-iteration count (QA 20, KPI 50, glossary 60), a safety ceiling on total tool calls independent of iterations (QA 6, KPI 30, glossary 80), and a per-call max-token budget. Tool results fed back are row-capped at 8 for QA and 20 for KPI. And only the last three tool results are retained in full — older ones are stubbed — so context doesn't grow unbounded across iterations.

Q36How does the KPI agent work, and why is there no fallback?

The agent explores the live database through tools and emits finalized KPI SQL with real table and column names. The runner re-executes every KPI itself under a row cap and statement timeout so a model-written query can't wedge the service, asks the chart picker for a Vega-Lite spec derived from the actual result shape, and persists KPI, value and chart.

No template fallback is deliberate: a generic template dashboard looks authoritative but is disconnected from the customer's real schema. A plausible-but-wrong dashboard damages trust more than an empty state does.

Q37What is the conversational glossary and why does it matter?

It's how users correct the agent in English instead of filing a ticket. Someone says "active customer should only count people who ordered in the last 90 days"; the edit endpoint translates that into a structured recipe change and returns an old→new diff; it applies only on confirm. Terms are versioned and revertible, and there's a lighter "this chat only" ad-hoc option scoped to a conversation in memory.

Why it matters: it moves the semantic layer from something a data engineer maintains to something the business owner maintains, and closes the loop from a bad answer to a permanent fix in one conversation. Notably the pipeline deliberately does not cache catalog bindings across turns, precisely so an edit takes effect on the very next question.

F · Safety, security, governance

Q38The DB role is read-only. Why still need a SQL safety gate?

Defence in depth plus three failure modes read-only doesn't cover. "Read-only" is a deployment claim you can't verify at runtime — a misconfigured customer credential is exactly the case you need protection for. It doesn't stop exfiltration primitives like INTO OUTFILE, load_file() or xp_cmdshell. And it doesn't stop resource exhaustion — an unbounded SELECT *, or benchmark()/pg_sleep() as a DoS. The gate blocks all three and injects a row cap when the model forgets one.

Q39Walk through the safety gate's checks in order.
  1. Reject empty SQL.
  2. Case-insensitive forbidden-substring scan.
  3. Parse with sqlglot at the target dialect.
  4. Top-level node must be Select, With, or a set operation.
  5. Walk the entire tree rejecting Insert/Update/Delete/Create/Drop/Alter/Truncate/Merge/raw Command nodes anywhere, including nested.
  6. Table allow-list from the retrieved slice.
  7. Column-existence check with alias and CTE-alias resolution; unqualified columns must exist on at least one FROM/JOIN table, not merely somewhere in the slice.
  8. PII-in-projection check.
  9. Inject a dialect-correct row cap if no LIMIT is present.
Q40What's the PII rule exactly, and why projection-only?

Columns tagged pii, financial or health may appear in WHERE, JOIN and GROUP BY — those filter rows and don't return sensitive values — but not raw in the SELECT projection unless wrapped in an aggregate. So SELECT COUNT(DISTINCT email) FROM users WHERE email LIKE '%@acme.com' is allowed; SELECT email FROM users is rejected with a message telling the model to aggregate instead. The check resolves table aliases so u.email is recognized as users.email, and unqualified columns are matched against every PII column in scope.

Q41What happens when sqlglot can't parse the SQL?

This was a real production problem. sqlglot is incomplete for some dialects — ClickHouse especially, where function-arity validation trips on valid nested duration math. Hard-rejecting killed valid queries after the whole repair budget was spent, and the model can't "fix" SQL that was never wrong; it regenerates the same valid ClickHouse and gets rejected again.

So a parse failure falls back to AST-free checks — no chained statements, must begin SELECT/WITH/parenthesised select, append a row cap — and lets the source DB validate the rest through the execute-and-repair loop.

The important bitIt fails closed when the schema has PII columns. Without an AST we can't prove PII isn't in the projection, so we refuse. Degrade availability, never confidentiality.

Q42How is multi-tenancy enforced?

Three layers. Identity — the 4-tuple key with unique constraints and endpoints that reject ambiguity instead of picking one. Authorization — ownership-sensitive endpoints check tenant and user against the catalog row and return 403; background scripts use an explicit system-user sentinel rather than a null that could match anything. Execution — the spec goes to the BI app with user and client headers, so the BI backend resolves the user profile and applies its own row- and column-level security. We don't reimplement RLS; we route through the system that already has it.

Q43What data do you deliberately not store, and why?

Raw result rows are not persisted in chat history — only question, answer text, generated SQL and the chart/dim-measure spec. Reopening replays the spec through the RLS path, which means a user who has lost access to some rows since the original answer doesn't see them on reload. The one exception is catalog-derived metadata answers (table lists, dimension values), stored inline because they aren't source PHI and their SQL is synthetic and non-executable. Config secrets are stored encrypted with a ~ marker and decrypted at read; sensitive datasource fields are redacted in logs.

G · Performance & scale

Q44Where does the latency go, and what did you do about it?

Per question: one router call, one synth call plus up to two repairs, one chart call, one embedding call, plus actual query execution. Optimizations roughly by impact — merged LLM calls (router does rewrite+classify, chart picker does chart+alternatives+caption); retrieval with no LLM at all; the deterministic embedding cache and the TTL question cache; plan snapshots that remove the report planner's LLM calls entirely; background catalog warm-up at boot; SSE with heartbeats so gateways don't 504 a long question; and progress beats published to a polling endpoint so the UI shows real steps instead of a spinner.

Q45How do you handle a database with thousands of tables?

Retrieval makes prompt size independent of schema size — that's the whole point. What is O(tables) is onboarding: introspection and profiling run on a thread pool with live intra-stage progress published so the bar interpolates within the profile stage instead of freezing while hundreds of tables are profiled. For genuinely large data there's an optional Spark profiler backend, auto-selected for Databricks or tables above 100M rows. And the pipeline is checkpointed, so a 30-minute onboarding that dies at stage 7 resumes at stage 7.

Q46How do you control LLM cost?

Named token budgets per prompt component, tests that fail the build when a budget is exceeded, per-request thread-local token accounting folded into the audit plan so every request's real cost is measurable, and caches that remove whole LLM calls rather than shortening them — plan snapshots remove the report planner entirely, the embedding cache removes embed calls. The honest gap: no per-tenant spend ceiling yet.

Q47Your caches are in-memory. What breaks at multiple instances?

Correctness doesn't break — every cache is either provably deterministic (embeddings) or TTL-bounded with explicit invalidation. What breaks is hit rate: each instance warms its own cache, so N instances mean roughly 1/N effective hit rate, and a refresh that invalidates on one instance doesn't invalidate on the others — which is why the TTLs are deliberately short. The documented upgrade path is Redis, and the modules are written so swapping the backing store is a local change, the same way the job submit() call is the single swap point for moving to a real queue.

H · Reliability, testing, reflection

Q48How does a long multi-stage onboarding survive crashes?

Four mechanisms. Checkpointing — each stage writes last_completed_stage; a re-entered run skips everything at or before it, and unknown stage names are defensively treated as not-done. Startup sweeps — rows stuck in INTROSPECTING over 30 minutes are bounced back to PENDING, with the same pattern for stale dashboards and document jobs. Status as the contract — the BI app polls connection status, and /ask returns 409 until ready, so a half-onboarded source can't be queried. Reloader disabled by default — Werkzeug's watchdog would kill long-lived onboarding threads and a double import would create two thread pools.

Q49How do you test an LLM-dependent system?

Four layers, all offline. Stubbed LLMs — a scripted client returns canned completions so a test asserts on our logic. Contract tests — response envelope, narrative API, renderer output — which is what makes the "every key always present" guarantee real rather than aspirational. Budget tests that fail if a prompt change blows a token budget. Named regression tests — files encoding specific production bugs so a fix can't silently regress.

What's missing, and I'd say so: an end-to-end evaluation set scoring answer correctness over a golden question bank. Contract tests prove the pipeline holds its shape; they don't prove the answer is right.

Q50What did you learn from this project?

One: the LLM is the smallest part of the system. The router, synth and chart calls are maybe 200 lines of prompt. The other 75,000 lines are retrieval, validation, caching, refusal logic, resumability and transparency — the machinery that makes a probabilistic component safe to put in front of a customer's database.

Two: constrain the output, not the model. Every quality jump came from narrowing what the model was allowed to emit — free SQL to validated spec, free chart choice to a constrained enum, free answers to explicit refusal exceptions. A model that can only emit valid shapes doesn't need to be trusted as much.

Three: an error message is a prompt. Rewriting rejections to collect all failures at once and include "did you mean" suggestions fixed more real failures than any tweak to the main synth prompt. The model is a consumer of your error strings — write them for that reader.
