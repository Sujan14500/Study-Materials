LangGraph is two ideas with a lot of consequences: explicit state that every node reads and writes, and a checkpoint written after every step. From those two you get cycles, resume-after-crash, pause-for-a-human, and rewinding a run to change one value and try again. Fifteen chapters, every idea attached to something you can step and break.

Chapter 1 · Foundations

Two questions, and only two

Does control flow ever need to go backwards? Does a run need to survive the process it started in? If both answers are no, an LCEL chain is smaller, faster and has nothing to configure. If either is yes, no amount of chain cleverness gets you there — you need a graph.

⛓️ LCEL

A chain is a DAG

Data flows forward. Every step runs once. The run lives and dies inside one call.

chain = prompt | model | parser
chain.invoke(x)
Tiny, fast, obviousNo loops, no pause
🕸️ LangGraph

A graph is a state machine

Nodes read and write one shared state. Edges can point anywhere, including backwards. State is checkpointed after every step.

builder.add_edge("rewrite", "retrieve")
graph = builder.compile(checkpointer=saver)
graph.invoke(x, {"configurable":
    {"thread_id": "t1"}})

Chapter 2 · Foundations

One typed dict, and the rules for merging it

A node does not mutate state — it returns a dict of updates, and LangGraph merges them in. How each key merges is decided by its reducer: overwrite by default, append if you say so. Getting one annotation wrong is the most common LangGraph bug, and it fails silently.

💻 Declaring state

from typing import Annotated, TypedDict
from operator import add
from langgraph.graph.message import add_messages

class State(TypedDict):
    question: str                             # overwrite
    steps: Annotated[list[str], add]          # append
    attempts: Annotated[int, add]             # sum
    messages: Annotated[list, add_messages]   # append, replace by id

# or start from the prebuilt one:
from langgraph.graph import MessagesState

class State(MessagesState):        # already has `messages`
    question: str
    attempts: Annotated[int, add]

A reducer is any f(existing, update) -> merged. Annotated[str, keep_longest] with your own function works exactly the same way.

📌 Five rules

⚠️
Two nodes, one super-step, one un-reduced key raises InvalidUpdateError. That is deliberate: with no reducer there is no rule for merging concurrent writes, so LangGraph refuses to guess rather than losing one silently. When you see it, you are being told to annotate the key — not to serialise the nodes.
Chapter 3 · Foundations

A node is just a function

Takes the state, returns a dict of updates. No base class, no decorator, nothing to inherit — which is why every node in this course is testable with a plain assert and no model in sight.

📌 Six things about wiring

⚡ Parallel is the default

Two edges out of one node means both branches run in the same super-step, concurrently. Fan-in waits automatically:

builder.add_edge("plan", "search_web")
builder.add_edge("plan", "search_docs")   # both run together
builder.add_edge("search_web", "merge")
builder.add_edge("search_docs", "merge")  # merge waits for both

Both branches write results, so that key needs a reducer — otherwise this is exactly the InvalidUpdateError from Chapter 2.

📤 Dynamic fan-out with Send

When you do not know the number of branches until run time — one per retrieved document, say — return Send objects:

from langgraph.types import Send

def fan_out(state: State):
    return [Send("summarise", {"doc": d})
            for d in state["docs"]]

builder.add_conditional_edges("retrieve", fan_out)

Each Send runs summarise with its own private input, all in one super-step. This is map-reduce, and the reduce half is just a reducer on the key they all write.

Chapter 4 · Control flow

A function that picks an edge

A conditional edge is a plain function taking the state and returning the name of the next node. Not data, not a boolean — a node name. Once that lands, routing, branching, looping and finishing are all the same mechanism.

Chapter 7 · Control flow

    
Scope the tools. Control the state.

    
A plain agent loop binds every tool to one model call and keeps everything it learns in the transcript. Both of those are decisions, and both are usually wrong. In a graph you can bind a different tool set to each node and give every state key exactly one writer — so "the model called the deploy tool during research" stops being a prompt-engineering problem and becomes something the schema cannot express.

Chapter 9 · Durability

    
Stop, ask a human, carry on tomorrow

    
Because the state is checkpointed, a graph can stop in the middle of a node and wait — not for a second, but for as long as it takes. The process can exit. The server can redeploy. When the answer arrives, the run continues from exactly where it paused.

💻 interrupt and resume

      

    

    

      
📌 Five things that bite

      

    

  


  

    
🔁

    
The node re-runs from the top. On resume, everything before interrupt() in that node executes a second time. If you sent an email above the interrupt line, you have now sent two. Keep side effects strictly after the interrupt, or in a node of their own.

  









  

    
Chapter 10 · Durability

    
Every past moment is addressable

    
Checkpoints are not just for resume. Each one has an id, so you can jump to the middle of a finished run, change a value, and run a different future from there — with the original branch left intact beside it.

Chapter 11 · Working with it

    
Five different things called "streaming"

    
A graph run emits state, per-node updates, model tokens, your own progress events, and execution traces. They are different streams, and stream_mode chooses which ones you get. Picking the wrong one is why "streaming does not work" is such a common complaint.

🎛️ Choosing in practice

      
    
        
  • Chat UI → ["updates", "messages"]. Updates drive the "thinking / searching" status line; messages drive the text appearing.
    • 
        
  • Filter by node. The metadata on each message chunk carries langgraph_node — stream tokens from generate and drop the ones from a grader the user should never see.
    • 
        
  • Long non-LLM work → "custom". Nothing else can see inside a node that is embedding 200 documents.
    • 
        
  • Nested graphs → add subgraphs=True, or a subgraph looks like one silent node.
    • 
        
  • Async → astream, same modes. astream_events exists for very fine-grained hooks, and is more than most UIs need.

Chapter 12 · Working with it

    
A graph inside a graph

📌 Five things about nesting

      

    

  


  

    
🎯

    
Nesting is a readability tool, not an intelligence one. Splitting one agent into five adds hand-off cost, lost context and five traces to correlate. Split when a subgraph is genuinely a separate concern with a separate tool set — or when one state schema has grown incoherent. Not because it looks more sophisticated on a diagram.

  









  

    
Chapter 13 · Working with it

    
The checkpointer is not memory

    
A checkpointer remembers this thread. When a user opens a new chat, that is a new thread and it knows nothing about them. Facts that should outlive a conversation go in the store — a separate thing, scoped by namespace rather than by thread.

Chapter 14 · Shipping

    
What breaks in production

    
Nearly every LangGraph production problem is one of four things: state that grew too big, a loop with no guard, a node that is not safe to re-run, or a node rename that broke resume for every in-flight thread. All four are cheap to prevent and expensive to discover.
