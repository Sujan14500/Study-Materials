Every structure is
a trade, never a winner

An array makes reading by position free and inserting in the middle expensive. A linked list swaps exactly those two. A hash table gives you instant lookup and takes away all ordering. Chapter 4 · Linear structures

The node — and everything built from it

🧩
Learn the node once and you have learned four chapters. A linked list is a node with one pointer. A binary tree is a node with two. A graph is a node with a list of them. A trie is a node with one per character. The wiring changes; the atom does not.

🔗 Three wirings

⚖️ Array vs linked list

The two structures are near mirror images. Neither wins — they are different points on the same trade.

🧊
The Big-O undersells the array. Linked lists look better on paper for insertion, but their nodes are scattered across memory while an array's elements are neighbours. The CPU fetches memory in chunks, so walking an array pulls the next elements in for free. In practice an array often wins even where the notation says it should lose — which is a useful reminder that Big-O is about growth, not speed.
Chapter 5 · Linear structures

Same items in. Different items out.

Both are collections you add to and take from. The only difference is which end you take from — and that single choice is the whole reason both exist. The restriction is the feature: because only one position is reachable, every operation is O(1) and the semantics are impossible to misuse.

📌 Six things worth knowing

🚫
What a hash table cannot do. "Give me the smallest key." "Give me everything between 10 and 50." "Iterate in order." A hash table has no ordering to offer — the position of a key is a function of its hash, which is deliberately unrelated to its value. If you need any of those, you want a tree. That is the next chapter, and it is not a coincidence.

📌 Six things worth knowing

🎯
Heap versus sorted list, in one line. A sorted list answers "what is the whole order?" and pays for it on every insert. A heap answers only "what is next?" and stays cheap. Priority queues never need the full order — so paying for it is pure waste, and the heap is the structure that declines to.

⚖️ Recursion vs iteration

💥
Stack overflow, plainly. Every call in progress occupies a frame holding its arguments and locals, and that memory is finite — typically a few thousand to a few tens of thousands of frames. Recurse down a million-element linked list and you will hit it. The fix is either an explicit stack of your own, or a loop.

Chapter 13 · Putting it together

Five shapes a solution can take

Almost every algorithm you meet is one of these five strategies applied to a particular problem. Recognising the shape is most of the work — once you know it is a DP problem, the rest is deciding what a subproblem is.

🗂️ The five

🎯 Name the paradigm

interactive

Six problems. Two of them are traps — a greedy answer that looks right and is not, and a divide-and-conquer that people reach for DP on.

🍽️
Greedy needs a proof, not a hunch. "Always take the biggest coin" gives the right answer for normal currency and the wrong one for denominations like {1, 3, 4} — greedy makes 6 as 4+1+1 while the answer is 3+3. Greedy algorithms are the fastest to write and the easiest to be quietly wrong with, which is why every real one comes with an exchange argument attached.
Chapter 14 · Putting it together

Match the structure to the operation you do most

You do not pick a data structure because it is interesting. You pick it by asking which operation you will perform thousands of times, and choosing whatever makes that one O(1) — then checking you can live with what it made expensive.

🧭
Four questions that settle it nearly every time. Do I look things up by key, or by position? Do I need them in order? Do I add and remove constantly, or build once and read many times? Is it always the newest, the oldest, or the smallest that I want next? Answer those and the structure is usually already chosen — the names in this course are just labels for the answers.
